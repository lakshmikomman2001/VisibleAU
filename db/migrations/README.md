# db/migrations — read this before touching drizzle-kit

## ⚠️ Never run `drizzle-kit generate` or `drizzle-kit push` in this repo

Migrations `0000`–`0011` were generated by drizzle-kit and are tracked in `meta/_journal.json` +
`meta/*_snapshot.json`. Migrations `0012` onward are **hand-written** and applied directly via
`psql -f db/migrations/00NN_name.sql` — they were never fed back into drizzle-kit's snapshot tracking.

This means drizzle-kit's own idea of "the current schema" is permanently stuck at migration `0011`. Running
`drizzle-kit generate` will:
- ignore ~18 migrations' worth of real schema history, and
- try to "catch up" by generating a new migration for everything since 0011 — including reusing migration
  numbers that already exist as hand-written files (confirmed: it once generated a file numbered `0012`,
  colliding with the real `0012_subscriptions_table.sql`).

Running `drizzle-kit push` is separately banned project-wide (see root `CLAUDE.md`) — it applies schema diffs
directly to whatever `DATABASE_URL` points at, bypassing the migration ledger entirely.

Both `pnpm db:generate` and `pnpm db:push` are wired to print this warning and exit 1
(`scripts/qa/guard-drizzle-kit.mjs`) rather than actually invoking drizzle-kit.

## What to do instead

- **Check for schema drift** (TS schema vs a live database): `pnpm db:drift` (needs
  `DATABASE_URL_FOR_DRIFT` set). This is the check that actually understands the full migration history,
  because it introspects the live database directly instead of relying on drizzle-kit's stale snapshot.
- **Make a schema change**: hand-write a new migration file (`db/migrations/00NN_description.sql`,
  idempotent — `IF NOT EXISTS` / `DO $$ ... EXCEPTION WHEN duplicate_object` guards, matching the style of
  `0026`–`0030`), review it, then apply with `psql -f`.

## Known gap this caused (fixed by migration 0030)

`0010_baseline-reconcile.sql` used `CREATE TABLE IF NOT EXISTS "organizations" (...)` to reconcile the full
desired shape of `organizations` — but since `organizations` was already created (without `slug` and
`onboarding_complete`) by `0000_marvelous_madrox.sql`, that statement was a silent no-op on any database that
replays migrations from a clean slate. `audits` has a related gap (`config_bundle_id`, `config_digest`,
`estimated_cost_cents`, `quality_status` — see `0010_phase2_sprint1_platform.sql:117-122`). `pnpm db:drift`
is what actually found both; `drizzle-kit generate`/`check` cannot, for the reason above.
